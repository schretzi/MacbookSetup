# Keybindings Reference

Generated by reading every config in this repo. Covers **kanata**, **skhd**,
**kitty**, and **neobean** (Neovim/LazyVim) in detail, since those are where
custom keymaps actually live. Other tools in the repo were checked and found
to define no keybindings of their own — see
[No keybindings found](#no-keybindings-found) at the bottom.

> **Scope note on neobean:** it's a LazyVim-based config, so LazyVim's own
> default keymaps still apply everywhere they aren't explicitly overridden
> here. This doc only lists what's *explicitly* configured in this repo, not
> the full LazyVim/Vim manual.

## 1. Kanata — system-wide key remapping

**Config:** [`kanata/kanata.kbd`](kanata/kanata.kbd)
Runs as a LaunchDaemon ([`kanata/com.kanata.daemon.plist`](kanata/com.kanata.daemon.plist)) and intercepts keys system-wide, before any app (including kitty) sees them. German QWERTZ layout; key names below are kanata's physical-position names, not printed characters.

| Key (physical) | Tap | Hold |
|---|---|---|
| `;` (prints `ö`) | ö | `\` (backslash, sent as literal unicode) |
| `'` (prints `ä`) | ä | `\|` (pipe) |
| `[` (prints `ü`) | ü | `~` (tilde) |
| Caps Lock | *nothing* | **Hyper**: holds Ctrl+Shift+Alt+Cmd together |

**"apps" layer** — active only while **`^`** (kanata name `nubs` — this key reports as `KEY_102ND`, the ISO "extra" key, *not* `KEY_GRAVE`/`grv` despite sitting where a US grave/backtick key would be; confirmed via `kanata --debug`, don't assume `grv` for this key on other keyboards without checking) is held. This is the dedicated app-switching layer; Hyper (Caps Lock) is intentionally kept for non-switching actions instead (see skhd below). `^` replaced an earlier fn-based trigger because fn sits far from the home row on a full-size external keyboard, and an even earlier "a"-based trigger because "a" is typed constantly and the tap/hold ambiguity made typing feel laggy. Unlike fn, `^` is a genuine tap-hold key (`caret_apps` alias, using `tap-hold-press`): tapping it still composes accents as normal (e.g. `^` then `a` → `â`), holding it activates the apps layer. `tap-hold-press` resolves to "hold" the instant another key (e.g. `k`) is pressed while `^` is still down, regardless of timing, so there's no perceptible delay on the shortcuts below; only a lone tap of `^` waits out the tap-timeout before typing the character.

| Key | Action |
|---|---|
| `^` + y *(physical "Z", German swap of Y/Z)* | Launch/switch to **Zen** |
| `^` + k | Launch/switch to **kitty** |
| `^` + b | Launch/switch to **Bitwarden** |
| `^` + c | Launch/switch to **Claude** |
| `^` + t | Launch/switch to **Microsoft Teams** |
| `^` + s | Go to (or launch) the **setup** dedicated kitty instance ([`kitty/sessions/setup.kitty-session`](kitty/sessions/setup.kitty-session)): cwd `~/Workspace/Schretzi/MacbookSetup`, opens neobean |
| `^` + d | Go to (or launch) the **daily-note** dedicated kitty instance: today's Obsidian daily note in neobean, creating it from the daily template if it doesn't exist yet ([`kitty/scripts/open-daily-note.sh`](kitty/scripts/open-daily-note.sh)) |
| `^` + o | Go to (or launch) the **obsidian** dedicated kitty instance ([`kitty/sessions/obsidian.kitty-session`](kitty/sessions/obsidian.kitty-session)): cwd `~/Obsidian/Documents/Schretzi`, opens neobean |
| `^` + r | Go to (or launch) the **work-network** dedicated kitty instance: three shells (VPN / Proxy / Tunneling). Session file and binding come from the work overlay; without it this key does nothing. |
| `^` + m | Go to (or launch) the **mail** dedicated kitty instance ([`kitty/sessions/mail.kitty-session`](kitty/sessions/mail.kitty-session)): runs neomutt; quitting neomutt closes the whole instance |
| `^` + F1 … `^` + F12 | Literal **F1–F12** (see the F-row table below for what these keys do *without* `^` held) |

Notes baked into the config itself: `^` + s / `^` + d call [`kitty-focus-or-launch.sh`](kitty/scripts/kitty-focus-or-launch.sh) / [`open-daily-note.sh`](kitty/scripts/open-daily-note.sh) — see §2 "Dedicated instances" for how those work and why plain `open -a kitty --args --session <file>` doesn't. fn is no longer listed in `defsrc` at all, so it's passed straight through unmodified — it may or may not regain its native macOS behavior (emoji picker/dictation/etc.), not verified. Hyper (Caps Lock hold) is consumed by skhd — see [§1a skhd](#1a-skhd--hyper-key-hotkeys) below.

**F-row (bare, `^` not held)** — F1-F12 are listed explicitly in `defsrc` and mapped to their stock macOS media-key actions, restoring the standard "bare F-key = media action, `^` + F-key = literal function key" behavior (kanata takes over the whole keyboard, so any key not listed in `defsrc` is passed through as a raw literal — this is what silently broke brightness/mute once kanata started managing this keyboard):

| Key | Action |
|---|---|
| F1 / F2 | Brightness down / up |
| F3 | Mission Control |
| F4 | Spotlight search |
| F5 | Dictation |
| F6 | Do Not Disturb |
| F7 / F8 / F9 | Previous track / play-pause / next track |
| F10 | Mute |
| F11 / F12 | Volume down / up |

### `ctrl+h` / `ctrl+j` / `ctrl+k` / `ctrl+l` — smart nvim-aware pane navigation

```
map ctrl+j kitten pass_keys.py bottom ctrl+j "nvim"
map ctrl+k kitten pass_keys.py top    ctrl+k "nvim"
map ctrl+h kitten pass_keys.py left   ctrl+h "nvim"
map ctrl+l kitten pass_keys.py right  ctrl+l "nvim"
```
Labeled in the config itself as *"Config from neovim plugin knubie/vim-kitty-navigator"*. This is **not** a plain window-nav shortcut — `pass_keys.py` checks whether the focused kitty window's foreground process matches the regex `n?vim`:
- **If nvim is running:** the raw `ctrl+h/j/k/l` keystroke is forwarded into nvim's stdin instead of moving kitty windows.
- **If nvim is not running:** kitty moves focus to the neighboring window itself.

This is designed to hand off to **[`neobean/lua/plugins/vim-kitty-navigator.lua`](neobean/lua/plugins/vim-kitty-navigator.lua)**, which catches `<C-h/j/k/l>` *inside* nvim (modes n/v/i) and calls `:KittyNavigateLeft/Down/Up/Right` — which in turn asks kitty to move focus when there's no more vim split in that direction. See [§4 The kitty ↔ neobean handoff](#4-the-kitty--neobean-handoff-and-why-it-can-appear-to-break) for why this is the exact behavior you noticed ("stops working once neobean is active").

**Dedicated instances** — `setup`, `obsidian`, `mail`, `daily-note` (and `work-network` from the work overlay) are genuinely separate OS-level kitty processes, not tabs muxed into one window. This replaced plain `goto_session` (which only ever affects the currently-focused window's tabs) after it caused exactly the bug it looks like: pressing a "go to X" shortcut while a different window had focus just changed *that* window's tabs instead of jumping to X. All of them are launched/focused via [`kitty-focus-or-launch.sh`](kitty/scripts/kitty-focus-or-launch.sh) `<session-file>`: it `pgrep`s for a process already running that exact `kitty --session <file>` command line, and if found, focuses it through *that instance's own* remote-control socket (`/tmp/kitty-<pid>` — every kitty process gets one, `listen_on` is global in kitty.conf); if not found, it does `open -a kitty -n --args --session <file>` (`-n`/`--new` forces a genuinely new instance — plain `open -a kitty --args ...` does *not* forward new `--args` to kitty's already-running singleton, it just refocuses whatever was already showing, which was the original bug). `open` is used deliberately over invoking the kitty binary directly — it detaches the new process cleanly regardless of the caller's own session, which matters since this also gets called from kanata's root LaunchDaemon.

**Cmd-Tab names & icons** — each dedicated instance runs from its own small app bundle in `~/Applications/Kitty Sessions/`, so macOS's app switcher shows `Setup` / `Obsidian` / `Neomutt` / `Daily Note` (plus any overlay session) with a distinct coloured, lettered icon instead of five identical `kitty` entries. This is needed because Cmd-Tab switches *applications* and takes its name from the bundle's `CFBundleName` — there's no per-process override, and every instance executing `/Applications/kitty.app` means they all read "kitty" (`lsappinfo list` shows them as identical entries). Window titles were always correct; they just never reached Cmd-Tab (they do show in Mission Control, Cmd-` cycling, and the Dock's window list).

The bundles are generated by [`kitty/scripts/make-session-apps.sh`](kitty/scripts/make-session-apps.sh) from the table in [`kitty/session-apps.conf`](kitty/session-apps.conf) (session glob → app name → icon letter → icon colour), with icons rendered by [`kitty/scripts/make-session-icon.js`](kitty/scripts/make-session-icon.js) through JXA's Objective-C bridge — AppKit is always present, unlike ImageMagick/librsvg/PIL. They're generated artifacts, not tracked in git; ~700 KB each, ~4 MB total. The structure copies kitty's own `kitty.app/Contents/kitty-quick-access.app`: own `Info.plist`, everything heavy symlinked back to the real install. `home` deliberately has no wrapper — it's the Dock icon / `startup_session` instance and should stay "kitty".

Two things worth knowing: the bundle's main executable must be a real **copy** of kitty's launcher (symlinking it fails to launch with `error -54`), so **re-run `make-session-apps.sh` after `brew upgrade kitty`**; and the wrappers strip `CFBundleDocumentTypes`/`CFBundleURLTypes`/`NSServices`/`CFBundleIconName` from kitty's plist, otherwise they'd each claim `.sh`/folders/`file:`/`git:` in every "Open With" menu and the asset-catalog icon would silently override the generated one. `kitty-focus-or-launch.sh` picks the wrapper up automatically and falls back to plain `kitty.app` for any session without one.

`daily-note` additionally goes through [`open-daily-note.sh`](kitty/scripts/open-daily-note.sh), which creates today's note (from `Templates/daily.md`) if missing, generates a *per-day* session file at `~/.cache/kitty-sessions/daily-note-YYYY-MM-DD.kitty-session` (not tracked in git), and hands that to `kitty-focus-or-launch.sh`. The per-day filename is what makes "always today's note" work: a window left open from a previous day has a different filename, so it's never mistaken for today's — it's simply left alone in the background, and a fresh dedicated instance opens for today.

`ctrl+b` is used as a **tmux-style prefix** — the config comment literally says *"This is similar to tmux prefix + key"* — even though tmux itself isn't used; kitty sessions replace tmux here (see the "Kitty Sessions section (To replace tmux)" comment block).

| Key | Action |
|---|---|
| `ctrl+b`→`i` | Launch/open daily note (same `open-daily-note.sh` as `^` + d in kanata — see §1) |
| `ctrl+b`→`n` | Browse & select from known projects (session picker) |

**`home`** ([`kitty/sessions/home.kitty-session`](kitty/sessions/home.kitty-session)) is the main/default session — plain shell at `~`, tab layout `tall`. It's kitty's `startup_session`, i.e. what a cold-launched kitty opens into; it isn't one of the dedicated instances above and has no dedicated hotkey of its own.

## 4. The kitty ↔ neobean handoff (and why it can appear to break)

Your example — "ctrl-h/j/k/l moves between kitty windows, but stops working once neobean is active" — is actually **by design**, not an accident, but it depends on a chain of three things all being true simultaneously:

1. `kitty.conf` maps `ctrl+h/j/k/l` to the `pass_keys.py` kitten, which checks the *foreground process name* of the focused kitty window against the regex `n?vim`.
2. If that matches, the raw keystroke is written into nvim's stdin instead of moving kitty windows.
3. Inside nvim, `vim-kitty-navigator.lua` must be loaded and must own `<C-h/j/k/l>` to catch that keystroke and translate it into `:KittyNavigate*` — which itself shells back out to a copy of `pass_keys.py`/companion scripts that the plugin's `build` step copies into `~/.config/kitty/` (`build = "cp ./*.py ~/.config/kitty/"`).

So it is **meant** to feel seamless: inside nvim, `ctrl+h/j/k/l` moves vim splits and falls through to kitty windows at the edges; outside nvim, it moves kitty windows directly. Within this repo's neobean config there's no competing binding for those keys — the old plain window-nav mappings are commented out specifically to avoid clashing with this plugin (`keymaps.lua:302-305`).

**If it's not working for you in practice**, the likely causes are outside the keymap files themselves:
- The plugin's `build` step (`cp ./*.py ~/.config/kitty/`) never ran, so kitty's copy of the navigator's companion script is stale or missing.
- `pass_keys.py`'s process match (`n?vim`) isn't matching your actual foreground process name — e.g. if you run nvim through a wrapper/alias whose process name doesn't contain "nvim" (worth checking with `ps` while nvim is focused).
- `NVIM_APPNAME=neobean` sessions launch a different process name than plain `nvim` in some code paths (e.g. the scrollback-viewer flow at `kitty.conf:399`) — worth confirming the regex still matches those.

This is the one genuine cross-tool "duplicate binding" in your setup — same key combo, two tools, resolved via a handoff mechanism rather than one owner — everything else below is either resolved deliberately or a smaller in-app annoyance.
