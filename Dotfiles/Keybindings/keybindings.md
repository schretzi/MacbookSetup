
# Keybindings Reference

Generated by reading every config in this repo. Covers **kanata**, **skhd**,
**kitty**, and **neobean** (Neovim/LazyVim) — those are where custom keymaps
actually live. Other tools in the repo were checked and found to define no
keybindings of their own — see
[No keybindings found](#no-keybindings-found) at the bottom.

Each app now has its own dedicated cheatsheet file, with **both the app's
own default keybindings and this repo's custom overrides/additions** side by
side, so you can see at a glance what's stock vs. what's been changed:

- [`kanata.md`](kanata.md) — system-wide key remapping
- [`skhd.md`](skhd.md) — Hyper-key hotkeys
- [`kitty.md`](kitty.md) — terminal emulator
- [`neobean.md`](neobean.md) — Neovim/LazyVim config

This file itself only keeps the **cross-app/overview** material that doesn't
belong to a single tool: the kitty↔neobean handoff mechanism, the
duplicates/conflicts summary, a master **all-custom-keybindings-sorted-by-key**
lookup table, and the "no keybindings found" list.

## The kitty ↔ neobean handoff (and why it can appear to break)

Your example — "ctrl-h/j/k/l moves between kitty windows, but stops working once neobean is active" — is actually **by design**, not an accident, but it depends on a chain of three things all being true simultaneously:

1. `kitty.conf` maps `ctrl+h/j/k/l` to the `pass_keys.py` kitten, which checks the _foreground process name_ of the focused kitty window against the regex `n?vim`.
2. If that matches, the raw keystroke is written into nvim's stdin instead of moving kitty windows.
3. Inside nvim, `vim-kitty-navigator.lua` must be loaded and must own `<C-h/j/k/l>` to catch that keystroke and translate it into `:KittyNavigate*` — which itself shells back out to a copy of `pass_keys.py`/companion scripts that the plugin's `build` step copies into `~/.config/kitty/` (`build = "cp ./*.py ~/.config/kitty/"`).

So it is **meant** to feel seamless: inside nvim, `ctrl+h/j/k/l` moves vim splits and falls through to kitty windows at the edges; outside nvim, it moves kitty windows directly. Within this repo's neobean config there's no competing binding for those keys — the old plain window-nav mappings are commented out specifically to avoid clashing with this plugin (`keymaps.lua:302-305`).

**If it's not working for you in practice**, the likely causes are outside the keymap files themselves:

- The plugin's `build` step (`cp ./*.py ~/.config/kitty/`) never ran, so kitty's copy of the navigator's companion script is stale or missing.
- `pass_keys.py`'s process match (`n?vim`) isn't matching your actual foreground process name — e.g. if you run nvim through a wrapper/alias whose process name doesn't contain "nvim" (worth checking with `ps` while nvim is focused).
- `NVIM_APPNAME=neobean` sessions launch a different process name than plain `nvim` in some code paths (e.g. the scrollback-viewer flow at `kitty.conf:399`) — worth confirming the regex still matches those.

This is the one genuine cross-tool "duplicate binding" in your setup — same key combo, two tools, resolved via a handoff mechanism rather than one owner — everything else below is either resolved deliberately or a smaller in-app annoyance.

See [`kitty.md`](kitty.md#ctrlh--ctrlj--ctrlk--ctrll--smart-nvim-aware-pane-navigation) and [`neobean.md`](neobean.md#cross-window--pane-navigation) for the two sides of this handoff.
